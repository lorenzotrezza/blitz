## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Hairline meter ticks, chip inner gaps, RPM window marker offsets |
| sm | 8px | Compact HUD gaps, shift quality badge padding |
| md | 16px | Default HUD/control spacing, safe gap between track and overlays |
| lg | 24px | Landscape edge padding, separation between track, HUD rail, and controls |
| xl | 32px | Gap between throttle and shift zones when controls are side-by-side |
| 2xl | 48px | Major separation between HUD groups and non-overlapping track regions |
| 3xl | 64px | Page-level fallback spacing only outside active fullscreen gameplay |

Exceptions: CSS `env(safe-area-inset-*)`, `100dvh`, `100vw`, and canvas aspect sizing are allowed because the shell must respect phone browser chrome and OS gesture areas. Drag controls must keep fixed multiples of 4: throttle hold zone 112px minimum wide by 88px minimum tall, shift button 88px minimum square, and any keyboard-focus target 56px minimum. The RPM/shift meter must keep a stable 40px minimum height so perfect/good/early/late feedback cannot resize the HUD.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 | 1.5 |
| Label | 12px | 400 | 1.3 |
| Heading | 20px | 600 | 1.2 |
| Display | 28px | 600 | 1.1 |

Rules:
- Use exactly these four sizes in the drag gameplay screen, controls, HUD, empty state, error state, and result summary.
- Use only weights 400 and 600.
- Letter spacing is `0` for all gameplay HUD and control text.
- Display text is reserved for countdown/go, finish time, or the current shift result. Do not use display sizing inside compact telemetry chips.
- Existing sub-12px pixel-font styles are not allowed for RPM, gear, speed, distance, shift quality, errors, or control labels.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#06060d` | Fullscreen drag background, straight track backing field, non-interactive empty regions |
| Secondary (30%) | `#0f0f1e` | HUD plates, RPM meter well, control wells, compact status strips |
| Accent (10%) | `#ffd700` | Ideal shift window, active throttle state, perfect shift feedback, countdown/go value, one mode-critical HUD value, focus ring |
| Destructive | `#ff3333` | Late shift penalty, connection errors, unavailable/blocked control state, destructive confirmations if later added |

Accent reserved for: the visible ideal shift window, pressed throttle highlight, perfect shift result, countdown/go indicator, one mode-critical HUD value, and keyboard focus ring. Do not apply accent to every meter tick, every button, decorative borders, or all labels.

Additional existing colors may be retained with fixed meanings: `#00aadd` for early/low-RPM telemetry and secondary track guide lines, `#33ff66` for good shift feedback or live/ready state, and `#ddeeff` for readable primary text. Shift quality must never rely on color alone; the text labels `EARLY`, `GOOD`, `PERFECT`, and `LATE` must be visible.

- Speed label: `KM/H`

- Error copy must pair a plain problem with one next action.

## Phase Interaction Contract

### Fullscreen Drag Layout

- Render `race:drag-sprint` as a fullscreen gameplay route using the Phase 1 `FullscreenGameShell` contract.
- The straight drag track is the main visual surface and must occupy the center of the viewport. HUD stays top/side; controls stay fixed at the bottom thumb zones.
- Landscape phone is the default target. Portrait must remain playable by stacking HUD top, track middle, and controls bottom without page scrolling.
- Normal app chrome, scanlines that reduce readability, card grids, page panels, and top navigation must be hidden or excluded during active drag gameplay.
- The track must communicate straight-line progress only: lane center, distance markers, player car, optional opponent/ghost cars, and finish line. Do not render steering lanes, obstacles, pickups, powerups, analog vectors, or lap/checkpoint UI in this phase.

### Drag HUD

- Required React-rendered fields: RPM, current gear, speed, distance, last shift quality, race status, and finish time after completion.
- Mode-critical slot: RPM plus ideal shift cue. This must be the most prominent active-play HUD element.
- RPM cue: use a horizontal or arc meter with a stable visual fill, a clearly marked ideal window, and a current RPM indicator. The ideal window must be visible before the shift is required, not only after the player misses it.
- Gear display: show `GEAR 1/4`, `GEAR 2/4`, `GEAR 3/4`, or `GEAR 4/4`.
- Distance display: show current distance and target distance in meters, for example `312 / 402 M`.
- Last shift display: reserve a stable chip area for `EARLY`, `GOOD`, `PERFECT`, `LATE`, or `--` before the first shift.
- Use an `aria-live="polite"` region for countdown, shift quality changes, finish state, and connection/error state. Do not announce every RPM, speed, or distance tick.

### Touch Controls

- Use two-thumb drag controls, not analog steering:
  - Bottom-left fixed hold zone: throttle. The player must press and hold to accelerate.
  - Bottom-right fixed action zone: shift. The player taps once per gear shift.
- Throttle visual states: idle, pressed, disabled, keyboard-focused. Pressed state may use accent fill but cannot change the control dimensions.
- Shift visual states: ready, tapped feedback, locked/unavailable, disabled, keyboard-focused. A tapped shift must produce immediate local visual feedback while the server-authoritative shift result arrives.
- Shift is a discrete action event. Holding the shift button must not repeatedly shift unless the shared input contract explicitly sends separate intentional events.
- Controls use Pointer Events with pointer capture where supported and set `touch-action: none`, `user-select: none`, and `-webkit-user-select: none`.
- Pointer cancel, touch cancel, mouse leave, blur, visibility change, route unmount, race finish, and connection loss must reset throttle to released.

### Keyboard And Desktop Fallback

- Throttle hold fallback: `Space` and `ArrowUp` while pressed.
- Shift fallback: `Shift` and `Enter` as discrete keydown actions. Ignore key-repeat for shift.
- Keyboard controls must share the same visual pressed/focused states as touch controls.
- Focus order: throttle, shift, optional exit/back control, then any non-gameplay controls.
- Focus ring uses `#ffd700` and must remain visible over dark surfaces.

### Shift Feedback

- Shift quality feedback must be immediate and testable in React-rendered text.
- `PERFECT` is the strongest positive feedback and uses accent. `GOOD` uses green. `EARLY` uses cyan/secondary telemetry. `LATE` uses destructive red.
- Feedback duration must be long enough to read during play: keep the last shift visible until the next shift or finish.
- Avoid camera shake, haptics, and sound as required mechanics in this phase. They can be added later only as nonessential polish.
- A bad shift must look recoverable. Do not use full-screen failure states for early or late shifts.

### Results Summary

- Results must include finish time and shift performance summary.
- Required result fields: finish time, rank/order if multiplayer, perfect shift count, good shift count, early shift count, late shift count, and total shifts.
- Result summary must use React-rendered text, not canvas-only graphics.
- The result page may reuse existing `ResultsPage` structure, but drag-specific summary content must be visible without opening a modal or expanding hidden details.

### Accessibility And Testability

- Do not make color the only indicator for the ideal shift window or shift quality; combine color, label text, and meter position.
- Buttons must expose accessible names `THROTTLE` and `SHIFT`.
- Throttle must expose pressed state with `aria-pressed` or equivalent testable state.
- Countdown, status changes, shift quality, and finish state must be inspectable in DOM text.
- Canvas, if used for the track, must have a concise accessible label such as `Straight drag race track`; detailed gameplay state remains in the React HUD.

### Shared Contract Expectations

- Shared input/snapshot foundations must remain in `packages/shared/src`, consumed by both web and server.
- Drag input must distinguish throttle pressed/released from shift action. Minimum payload concepts: input kind, pressed state for throttle, discrete shift action, sequence/tick, and client timestamp.
- Drag snapshot must expose: status, countdown, player progress, speed, distance, RPM, gear, max gears, shift window bounds or equivalent cue data, last shift quality, and finished result fields.
- Results summary must expose shift counts by `early`, `good`, `perfect`, and `late`.
- Client visuals are derived from server snapshots. Client-side pressed feedback is allowed for responsiveness, but final speed, RPM, distance, shift quality, finish time, and ranking are server-authoritative.
