## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Obstacle warning icon gaps, HUD chip inner separators, lane marker offsets |
| sm | 8px | Compact HUD chip gaps, road edge marker spacing, control label gaps |
| md | 16px | Default HUD/control spacing, safe gap between road and overlays |
| lg | 24px | Landscape shell edge padding, control cluster padding |
| xl | 32px | Separation between steering control and road edge or result summary groups |
| 2xl | 48px | Major separation between HUD groups and bottom control area |
| 3xl | 64px | Page-level fallback spacing outside active fullscreen gameplay only |

Exceptions: CSS `env(safe-area-inset-*)`, `100dvh`, `100vw`, canvas aspect sizing, and normalized road coordinates are allowed. Gameplay targets remain fixed multiples of 4: steering pad 176px by 96px minimum in landscape, 144px by 88px minimum in portrait, HUD chips 44px minimum height, warning chips 56px minimum width, and keyboard-focus target 56px minimum. Existing 1px/2px/4px borders may be reused.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 | 1.5 |
| Label | 12px | 400 | 1.3 |
| Heading | 20px | 600 | 1.2 |
| Display | 28px | 600 | 1.1 |

Rules:
- Use exactly these four sizes for the dodge race route, HUD, controls, empty state, error state, and result summary.
- Existing sub-12px pixel-font styles are not allowed for obstacle warnings, speed, distance, slowdown, hit count, controls, errors, countdown, or finish text.
- Letter spacing is `0` for gameplay HUD and control text. Existing brand-style wide letter spacing stays outside the fullscreen route.
- Display text is reserved for countdown, finish time, or the active slowdown warning. Do not use display sizing inside compact HUD chips.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#06060d` | Fullscreen game background, road backing field, non-interactive empty regions |
| Secondary (30%) | `#0f0f1e` | HUD plates, control well, result summary strips, compact overlay surfaces |
| Accent (10%) | `#ffd700` | Active steering vector, next obstacle warning, focus ring, countdown/go value, distance progress highlight |
| Destructive | `#ff3333` | Collision flash, slowdown state, hit count alert, connection errors only |

Accent reserved for: active steering vector/knob, incoming obstacle warning state, countdown/go indicator, distance progress value, and keyboard focus ring. Do not apply accent to every HUD border, all lane lines, decorative backgrounds, or inactive controls.

Additional existing colors may be retained only for limited meanings: `#00aadd` for secondary telemetry such as speed labels or lane guide lines, `#33ff66` for clear/race-live state, and `#ddeeff` for readable primary text. Obstacles should use high-contrast red/orange treatment against the road, but collision state must use `#ff3333` consistently.

## Phase Interaction Contract

### Fullscreen Dodge Shell

- Render the straight obstacle race in the Phase 1 fullscreen gameplay shell, not inside normal app chrome, `.panel`, `.card`, `.viewport`, or the existing live race grid.
- Shell dimensions: `width: 100vw`, `min-height: 100dvh`, `overflow: hidden`, and route-level containment that prevents page scrolling during play.
- Keep landscape phone as the primary target. Portrait must remain playable by stacking HUD top, road middle, and steering pad bottom without vertical scroll.
- The road/canvas is the primary visual surface and occupies the center of the viewport. HUD overlays stay top/side; controls stay bottom and never cover the player's car.
- Respect safe areas on every edge using CSS `env(safe-area-inset-*)` with at least 16px visual padding.

### Road And Obstacle Readability

- Use a straight vertical road with 3 visual guide lanes, but player movement is continuous horizontal position, not lane-snap movement.
- Player car sits in the lower 22-28% of the road area so incoming obstacles have visible preview distance.
- Obstacles enter from the upper road/horizon and move toward the car. At least the next wave must be visible before collision range.
- Obstacle warnings must be readable from the road first: use obstacle silhouettes, lane/position danger highlights, and an optional compact `Obstacle ahead` HUD chip.
- Seeded waves should escalate by spacing and density, not by making obstacles visually ambiguous. Early waves leave at least one obvious escape path.
- Obstacle bounds must be visually aligned with collision bounds. Do not draw narrow art with wide invisible hit boxes.
- Do not render pickups, nitro, shields, repair, RPM meters, shift bands, lap counters, or checkpoint gates in this mode.

### Steering Control

- Use a `DodgeSteeringPad` or equivalent continuous horizontal control in the bottom-left or bottom-center thumb zone.
- Steering pad minimum size: 176px by 96px landscape, 144px by 88px portrait. It emits normalized `steerX` from `-1` to `1`; neutral is `0`.
- Dragging inside the pad updates `steerX` continuously. Holding left/right halves may also emit continuous intent, but it must still produce smooth horizontal car movement.
- Releasing, pointer cancel, blur, visibility change, route unmount, or lost pointer capture resets steering to `0`.
- Controls use Pointer Events with pointer capture where supported and set `touch-action: none`, `user-select: none`, and `-webkit-user-select: none`.
- Visual feedback is required for neutral, active-left, active-right, disabled, and keyboard-focused states. Feedback must not change control dimensions.
- This phase does not require a primary action button during active play. If the shared shell expects an action slot, render it inactive or omit it rather than inventing throttle, brake, shift, or powerup behavior.

### Keyboard And Desktop Fallback

- Direction fallback: `ArrowLeft`/`A` steer left and `ArrowRight`/`D` steer right through the same normalized steering contract.
- Releasing either key returns that direction to neutral unless the opposite direction remains held.
- Desktop fallback is for testing and casual play; touch steering remains the primary design target.
- Focus order: road status/HUD, steering pad, exit/back control if present. Focus ring uses `#ffd700` and remains visible over dark surfaces.

### HUD Contract

- HUD is React-rendered text outside the canvas so tests and accessibility checks can inspect it.
- Required fields: mode objective, distance, speed, obstacle warning state, hit count, and slowdown/recovery state.
- HUD position: top edge in landscape; top plus one side rail is allowed on wide screens. HUD must not overlap bottom controls or hide incoming obstacles.
- The warning chip may use accent while an incoming obstacle wave is active. Collision/slowdown chips use destructive red for the 1-1.5s recovery window.
- Use an `aria-live="polite"` region for countdown, warning transitions, collision/slowdown state changes, and finish state. Do not announce speed or distance every tick.
- Critical values must remain readable at phone size: use 16px body for values and 12px labels at minimum.

### Collision And Slowdown Feedback

- On hit, show immediate road feedback and HUD feedback in the same frame or next render tick.
- Required feedback: speed value drops, slowdown state becomes visible, hit count increments, and the car/road shows a brief red flash or outline.
- Slowdown recovery lasts approximately 1-1.5s in the first tune. The UI should show recovery as a temporary state, not as permanent failure.
- One hit must feel recoverable; repeated hits must be visually understandable through the hit count and final time.

### Results Contract

- Results must include finish time and obstacle hit count for each player.
- Result summary labels: `Finish time`, `Obstacle hits`, and `Best dodger` when a winner summary is available.
- Do not show drag shift quality counts, RPM, gear, lap, checkpoint, pickup, or powerup summaries in Phase 3 results.
- If no mode-specific result data is present, render a dodge-specific empty summary: `No obstacle summary received. Finish order is still recorded.`

### Shared Contract Expectations

- Shared dodge input/snapshot/result fields belong in `packages/shared/src/game.ts` or adjacent shared exports, not local-only component state.
- Input payload must be discriminated for dodge steering or mode input. Minimum concepts: `mode: 'straight-obstacle'` or equivalent, `steerX`, `sequence` or `tick`, and client timestamp.
- Snapshot must support: `sessionId`, `modeId` or `trackId`, `status`, `countdown`, players, distance/progress, speed, obstacle warnings, active obstacles, hit count, slowdown/recovery state, and finish data.
- Results summary must support finish time and obstacle hit count.
- Server remains authoritative. Client visuals may interpolate for smoothness, but collision, speed penalty, recovery, and final hit count come from server snapshots/results.
